## Current structured-data status

The current page templates do not emit JSON-LD.

Repository searches for `ld+json` returned no implementation. A search for `schema.org` only found the internal JSON Schema file used to describe the TWG business-directory data shape; that file is not Schema.org webpage markup.

`src/layouts/BaseLayout.astro` currently emits canonical, Open Graph, Twitter-card, title, description, image and favicon metadata, but no `<script type="application/ld+json">` block.

This is good news architecturally: JSON-LD can be added once at the template/utility layer rather than manually added to directory records.

## Event field mapping audit

Google's current Event structured-data documentation requires `name`, `startDate`, and a physical `location` with address information for physical events. TWG already has direct or resolved sources for these fields.

| TWG source | JSON-LD target | Status / rule |
| --- | --- | --- |
| `event.event_name` | `Event.name` | Clean direct mapping; required by Google. |
| `event.start_datetime` | `Event.startDate` | Clean mapping when emitted as valid ISO-8601 with the correct local offset. |
| `event.end_datetime` | `Event.endDate` | Clean optional mapping. |
| canonical event URL from `event_slug` | `Event.url` / stable `@id` | Clean generated mapping. |
| `event.description` | `Event.description` | Clean mapping. |
| `event.image_url` | `Event.image` | Clean mapping after converting relative URLs to absolute site URLs. |
| `resolveEventLocation(...).venueName` | `Event.location.name` | Clean resolved mapping. |
| resolved address | `location.address.streetAddress` | Clean when present. |
| resolved city | `location.address.addressLocality` | Clean when present. |
| resolved state | `location.address.addressRegion` | Clean when present. |
| resolved postal code | `location.address.postalCode` | Clean when present. |
| fixed country for current TWG US inventory | `location.address.addressCountry` | Emit only when applicable; current coverage is US. |
| resolved latitude/longitude | `location.geo` | Optional enhancement when coordinates are valid. |
| `status: canceled` | `EventCancelled` | Clean explicit mapping. |
| `status: postponed` | `EventPostponed` | Clean explicit mapping. |
| scheduled/upcoming/recurring current events | `EventScheduled` | Safe default unless a different Schema.org status is specifically justified. |
| `ticket_url` | `offers.url` | Emit only when URL actually provides ticket purchase/admission for the event. |
| `cost_type: free` | `offers.price: 0` | Safe only when the event is genuinely free of admission/service fees. |
| `cost_details` | no automatic numeric price | Human-readable text must not be guessed into a numeric offer price. |
| `host_business_slug` | `organizer` | Resolve to linked business/organization where appropriate. |
| `organizer_name` | `organizer.name` | Plain-text fallback when no canonical TWG host record exists. |
| categories/tags | optional Schema.org metadata | Not required for Google's Event rich result; do not block initial rollout. |

### Important Event edge cases identified

1. TWG supports `postponed` and `canceled`, which map cleanly to Google's supported event-status values.
2. TWG does not currently have a canonical `rescheduled` status or `previousStartDate` field. Do not invent these values. If TWG later needs explicit reschedule semantics, add them deliberately.
3. Recurrence is stored as TWG recurrence metadata. Google event eligibility is centered on single-event detail pages/occurrences; recurring-event handling needs a deliberate rule in Step 4 rather than blindly dumping an RRULE into Event markup.
4. Multiple simultaneous physical locations should not be represented as one ambiguous Google event location. Step 4 must define how TWG handles these records.
5. `ticket_url` is not automatically an Offer unless it is actually a ticket/admission landing page.

## Business/place field mapping audit

TWG already has strong raw inputs, but one universal Schema.org type would be inaccurate. The directory contains different entity classes, so Step 6 must create a type mapper.

| TWG source | JSON-LD target | Status / rule |
| --- | --- | --- |
| `business_name` | `name` | Clean direct mapping. |
| canonical URL from `slug` | `url` / stable `@id` | Clean generated mapping. |
| `description` / `short_description` | `description` | Clean mapping. |
| `website` | official URL / `sameAs` as appropriate | Clean when present. |
| `phone` | `telephone` | Clean mapping. |
| `email` | `email` | Clean mapping. |
| `logo_url` / `logo` | `logo` | Clean after absolute-URL normalization. |
| `image_url` / `image` | `image` | Clean after absolute-URL normalization. |
| Facebook / Instagram / YouTube / TikTok | `sameAs` | Clean mapping. |
| street/address + city/state/postal fields | `PostalAddress` | Clean when structured components exist. |
| latitude/longitude | `GeoCoordinates` | Clean when coordinates are valid. |
| `price_range` | `priceRange` | Appropriate for applicable LocalBusiness subtypes. |
| `hours` | `openingHoursSpecification` | Requires a parser/normalizer; do not emit malformed hours. |
| categories | `@type` selection | Requires centralized type-mapping rules. |
| parent/child/related relationships | Schema.org relationships | Do not auto-map until relationship semantics are defined in Step 8. |

### Type-mapping constraint

Do not mark every TWG directory record as `LocalBusiness`. The directory contains restaurants, marinas, stores, lodging, parks, universities, chambers/organizations, public facilities, attractions, event venues and other places/entities. Step 6 will map the strongest supported subtype where justified and use a conservative fallback when it is not.

## Proposed implementation boundary for Step 2

Create one reusable utility module responsible for:

1. absolute URL normalization;
2. pruning null/empty values;
3. safe JSON serialization for `<script type="application/ld+json">`;
4. building Event JSON-LD from existing event + resolved venue data;
5. later adding Organization, business/place and breadcrumb builders without duplicating logic in page templates.

The TWG JSON source files remain the source of truth. No directory-wide record conversion is required.
